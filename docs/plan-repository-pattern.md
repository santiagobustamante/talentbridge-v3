# Plan: Patrón repositorio en el backend

Extraer todo acceso directo a `this.prisma.<modelo>` de los `*.service.ts` a clases `*Repository` dedicadas (una por modelo de Prisma), agrupadas en `libs/repository` (`@app/repository`), `@Global()` igual que `PrismaModule`/`CommonModule`. Objetivo: los services quedan con lógica de negocio pura + orquestación de transacciones; toda consulta/escritura de un modelo vive en un solo lugar reutilizable entre servicios.

**Nota sobre el origen de este plan:** la Fase 1 (esta infraestructura base) no existía en el proyecto — se construyó recién ahora, el mismo día que se ejecutaron las Fases 2-9, a partir de un prompt que asumía que ya estaba hecha (ver `docs/DECISIONS.md` para el detalle de esa discrepancia y cómo se resolvió).

## Patrón base (aplica a todo repositorio, no se repite por fase)

- Un archivo por modelo de Prisma: `<modelo>.repository.ts`, clase `@Injectable() export class <Modelo>Repository`, constructor inyecta `PrismaService`.
- Cada método acepta un último parámetro opcional `tx?: Prisma.TransactionClient`, y resuelve `const client = tx ?? this.prisma;` antes de la llamada real — permite que el método participe de una transacción del service que lo llama sin duplicar la consulta.
- Nombre de método por lo que hace (`findByUserId`, `existsBetweenCandidateAndCompany`), no por la línea que reemplaza ni por el nombre del método de Prisma.
- La orquestación de una transacción (decidir qué operaciones van juntas, el `isolationLevel`, manejar el error específico de un conflicto) se queda en el service — el repositorio expone las operaciones sueltas que la transacción combina, no la transacción en sí.
- Se registra en `RepositoryModule` (`libs/repository/src/repository.module.ts`), `@Global()`.
- Import vía alias absoluto `@app/repository`, nunca relativo — no importa la profundidad de la carpeta del consumidor.
