# Plan: Panel de Administración — TalentBridge V3

**Estado: en construcción, iniciado el 30/07/2026.** Basado en la [auditoría del panel administrativo](#auditoría-de-referencia) hecha ese mismo día (investigación real de código con archivo:línea, no supuestos genéricos). Es una ampliación de alcance real — `docs/alcance-mvp.md` listaba "Panel administrativo" explícitamente fuera del MVP original — y se documenta como decisión en `DECISIONS.md`.

## Contexto

El usuario pidió un rol ADMIN capaz de modificar "TODO" — parámetros generales del sistema, catálogos, reglas de negocio, seguridad, integraciones, gestión de usuarios/empresas — con el panel "super bien estructurado y parametrizado". No existía absolutamente nada de esto: ni rol ADMIN, ni tabla de configuración, ni audit log, ni soft-delete en todo el proyecto.

## Decisiones de arquitectura tomadas

- **Nuevo microservicio dedicado `admin-service`** (puerto 3011) en vez de repartir endpoints admin entre servicios existentes — coherente con el resto del proyecto (10 microservicios detrás del gateway) y evita que un servicio de dominio (jobs, auth, etc.) cargue con responsabilidades de configuración transversal.
- **`SystemParameter`**: tabla genérica (key/category/type/value/defaultValue/min/max/allowedValues/description/riskLevel) — cada parámetro es una fila con metadata, no una constante de código. Así "parametrizar" es literal.
- **`SystemCatalog`**: tabla genérica para catálogos de opciones (tipos de contrato, modalidad, etc.). Regla no negociable: **nunca se borra una fila físicamente** (`active: false` en su lugar) — datos históricos pueden referenciar un valor dado de baja.
- **`AdminAuditLog`**: registra cada cambio (quién/qué/cuándo/antes/después/IP). No existía ningún mecanismo de auditoría en el proyecto — se construye desde cero y es requisito bloqueante antes de cualquier pantalla de edición, dado el poder del rol.
- **Login admin separado** (`POST /auth/login-admin`, ruta frontend `/admin/login`) — mismo patrón que `login`/`login-company` (cada uno rechaza los otros roles), no un endpoint nuevo de auto-registro. La primera cuenta ADMIN se crea con un script de un solo uso, nunca vía registro público.
- **Reuso total de patrones existentes**: `@Roles(UserRole.ADMIN)` + `RolesGuard` (backend, ya usado por CANDIDATE/COMPANY en 6 controllers), `AdminGuard` calcado de `CandidateGuard`/`CompanyGuard` (frontend), `AdminShellComponent` calcado de `app-shell`/`company-shell`.
- **Despliegue a producción (Railway/Render) de `admin-service` es un paso separado y explícito** — no se ejecuta hasta confirmación puntual, dado que crear un servicio nuevo en la nube es una acción de mayor riesgo/alcance que el resto del trabajo (que es local).

## Niveles de riesgo de los parámetros (define la fuerza de confirmación en la UI)

| Nivel | Qué incluye | Ejemplo |
|---|---|---|
| 0 | Secretos — nunca expuestos en ninguna UI | `JWT_SECRET`, `DATABASE_URL`, API keys |
| 1 | Catálogos — bajo riesgo, reversible | Tipos de contrato, modalidad, categorías de habilidades |
| 2 | Reglas de negocio | Umbral de match, rúbrica de CV, paginación |
| 3 | Seguridad | Rate limits, expiración de tokens, reglas de contraseña |
| 4 | Integraciones/IA | Modelo DeepSeek, remitente de correo |
| 5 | Gestión de datos reales | Suspender usuario, cerrar oferta ajena — el más sensible |
| 6 | Feature flags | Activar/desactivar Joaquín, análisis de CV, chat |

### Fase 5 — Seguridad (Nivel 3)
- [x] **Bug real corregido**: `JWT_EXPIRES_IN` estaba declarado en `.env.example`/`.env` desde antes pero `auth.module.ts` hardcodeaba `expiresIn: '1d'` sin leerlo nunca — config muerta. Ahora sí se lee (`jwtExpiresIn = process.env['JWT_EXPIRES_IN'] || '1d'`), sin cambiar el comportamiento actual (el valor en `.env` ya era `'1d'`).
- [x] **Endurecimiento nuevo**: las cuentas ADMIN firman con una sesión de 2 horas (no el `JWT_EXPIRES_IN` general, hoy 1 día) — dado el poder del rol, una sesión abierta y olvidada expira rápido. A propósito NO es un `SystemParameter` editable desde el propio panel (dejar que un admin extienda su propia sesión debilitaría la protección justo donde más importa).
- **Decisión consciente de NO parametrizar en esta fase:** los rate limits (`ThrottlerModule.forRoot(...)`, hoy 10/min login y 300/min general) — técnicamente **no son dinámicamente configurables** sin un refactor más profundo: `ThrottlerModule.forRoot` fija el límite al arrancar el proceso, no por request; hacerlos editables en caliente exigiría un guard custom que lea `SystemParameter` en cada request (con su propio costo de latencia/cache) en vez del `ThrottlerGuard` estándar de Nest. Se decidió **no fingir** una fila de `SystemParameter` para esto que un admin pudiera "editar" sin que tuviera efecto real — eso sería peor que no tener el campo. Queda anotado como trabajo futuro concreto, con el diseño ya pensado (guard custom + cache corto), no como un vacío sin explicar.
- **Probado:** build limpio. `npx jest apps/auth-service`: se encontró y corrigió una regresión real (un test esperaba `jwtService.sign` llamado con un solo argumento; mi primer intento pasaba un segundo argumento `undefined` para roles no-ADMIN, cambiando la firma de la llamada) — corregido separando el branch ADMIN del resto en vez de un argumento condicional. Verificado en vivo decodificando el JWT real: cuenta ADMIN → 2 horas de validez; cuenta CANDIDATE → 24 horas (sin cambio).
