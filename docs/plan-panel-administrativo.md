# Plan: Panel de Administración — TalentBridge V3

**Estado: en construcción, iniciado el 30/07/2026.** Basado en la [auditoría del panel administrativo](#auditoría-de-referencia) hecha ese mismo día (investigación real de código con archivo:línea, no supuestos genéricos). Es una ampliación de alcance real — `docs/alcance-mvp.md` listaba "Panel administrativo" explícitamente fuera del MVP original — y se documenta como decisión en `DECISIONS.md`.

## Contexto

El usuario pidió un rol ADMIN capaz de modificar "TODO" — parámetros generales del sistema, catálogos, reglas de negocio, seguridad, integraciones, gestión de usuarios/empresas — con el panel "super bien estructurado y parametrizado". No existía absolutamente nada de esto: ni rol ADMIN, ni tabla de configuración, ni audit log, ni soft-delete en todo el proyecto.

## Decisiones de arquitectura tomadas

- **Nuevo microservicio dedicado `admin-service`** (puerto 3011) en vez de repartir endpoints admin entre servicios existentes — coherente con el resto del proyecto (10 microservicios detrás del gateway) y evita que un servicio de dominio (jobs, auth, etc.) cargue con responsabilidades de configuración transversal.
- **`SystemParameter`**: tabla genérica (key/category/type/value/defaultValue/min/max/allowedValues/description/riskLevel) — cada parámetro es una fila con metadata, no una constante de código. Así "parametrizar" es literal.
- **`SystemCatalog`**: tabla genérica para catálogos de opciones (tipos de contrato, modalidad, etc.). Regla no negociable: **nunca se borra una fila físicamente** (`active: false` en su lugar) — datos históricos pueden referenciar un valor dado de baja.
- **`AdminAuditLog`**: registra cada cambio (quién/qué/cuándo/antes/después/IP). No existía ningún mecanismo de auditoría en el proyecto — se construye desde cero y es requisito bloqueante antes de cualquier pantalla de edición, dado el poder del rol.
- **Login admin separado** (`POST /auth/login-admin`, ruta frontend `/admin/login`) — mismo patrón que `login`/`login-company` (cada uno rechaza los otros roles), no un endpoint nuevo de auto-registro. La primera cuenta ADMIN se crea con un script de un solo uso, nunca vía registro público.
- **Reuso total de patrones existentes**: `@Roles(UserRole.ADMIN)` + `RolesGuard` (backend, ya usado por CANDIDATE/COMPANY en 6 controllers), `AdminGuard` calcado de `CandidateGuard`/`CompanyGuard` (frontend), `AdminShellComponent` calcado de `app-shell`/`company-shell`.
- **Despliegue a producción (Railway/Render) de `admin-service` es un paso separado y explícito** — no se ejecuta hasta confirmación puntual, dado que crear un servicio nuevo en la nube es una acción de mayor riesgo/alcance que el resto del trabajo (que es local).

## Niveles de riesgo de los parámetros (define la fuerza de confirmación en la UI)

| Nivel | Qué incluye | Ejemplo |
|---|---|---|
| 0 | Secretos — nunca expuestos en ninguna UI | `JWT_SECRET`, `DATABASE_URL`, API keys |
| 1 | Catálogos — bajo riesgo, reversible | Tipos de contrato, modalidad, categorías de habilidades |
| 2 | Reglas de negocio | Umbral de match, rúbrica de CV, paginación |
| 3 | Seguridad | Rate limits, expiración de tokens, reglas de contraseña |
| 4 | Integraciones/IA | Modelo DeepSeek, remitente de correo |
| 5 | Gestión de datos reales | Suspender usuario, cerrar oferta ajena — el más sensible |
| 6 | Feature flags | Activar/desactivar Joaquín, análisis de CV, chat |

### Fase 3 — Catálogos (Nivel 1)
- [x] `CatalogController`/`CatalogService` genéricos en `admin-service` (`GET /admin/catalogs` agrupado por `catalogKey`, `GET /admin/catalogs/:catalogKey`, `POST` para agregar valor, `PATCH /admin/catalogs/entry/:id` para editar label/orden/activo — **nunca** `DELETE`, un valor solo se desactiva).
- [x] Migrados de punta a punta (backend + frontend, no solo "sembrados"): `JOB_MODALITY` (3 valores), `JOB_CONTRACT_TYPE` (8 valores), `JOB_WORKLOAD` (6 valores) — los mismos que ya usaba `company-jobs`/`candidate-jobs`, sin cambiar ningún dato existente. `create-job-offer.dto.ts` pasó de `@IsIn(ARRAY_ESTATICO)` a `@IsString()+@MaxLength()`, con la validación real movida a `JobsService.assertValidCatalogValue()` (consulta `SystemCatalog` en cada `createJob`/`updateJob`). Nuevo endpoint `GET /jobs/catalogs` (cualquier usuario autenticado, no solo ADMIN) que sirve estos 3 catálogos; `company-jobs.component.ts`/`candidate-jobs.component.ts` los consumen ahí en vez de sus arrays hardcodeados (que quedan solo como respaldo visual mientras carga).
- [x] Nueva página admin "Catálogos" (`admin-catalogs.component.ts`) — tabla por catálogo con activar/desactivar y alta de valores nuevos.
- **Decisión consciente de NO migrar en esta fase:** categorías/niveles de habilidad, tipo de contrato y modalidad de `Experience` (candidato), tipo/nivel de formación educativa, tipo/estado de proyecto, monedas. Motivo: `Experience.contractType` (FULL_TIME/PART_TIME/CONTRACTOR...) y `JobOffer.contractType` (Término indefinido/Término fijo...) son conceptualmente **catálogos distintos** (uno es una clasificación genérica de experiencia laboral, el otro son los tipos de contrato legales colombianos) — la hipótesis inicial de "unificarlos" en el mismo catálogo era incorrecta y se descartó al mirar los datos reales; forzar un solo catálogo hubiera sido un error funcional. El catálogo de habilidades (`skill-catalog.ts`, ~600 entradas) necesitaría además un campo de agrupación (categoría) que el modelo `SystemCatalog` no tiene hoy — migrarlo a medias hubiera sido peor que dejarlo como está. Todo esto queda como trabajo futuro explícito, no fue un olvido.
- **Probado:** build limpio (backend + frontend). `npx jest`: sin regresiones nuevas. Verificado en vivo: `GET /jobs/catalogs` devuelve los 3 catálogos reales; crear una oferta con un valor de modalidad inventado devuelve 400 ("La modalidad no es un valor válido"); crear una con un valor real (Remoto/Otro/Flexible) funciona igual que antes (creada y luego borrada, era de prueba); página `/admin/catalogs` real en el navegador muestra los 17 valores correctos, agrupados y con su estado activo.

### Fase 4 — Reglas de negocio (Nivel 2)
- [x] Rúbrica de análisis de CV: los 5 pesos (antes hardcodeados en el prompt de `cv.service.ts`: 15/30/25/15/15) ahora viven en `SystemParameter` `CV_RUBRIC_WEIGHTS` (tipo JSON) — `getRubricWeights()` los lee e interpola en el prompt (incluido el total dinámico, ya no asume que siempre suman 100).
- [x] Paginación unificada: nuevo helper compartido `getPaginationLimits()`/`clampLimit()` (`libs/common/src/pagination/`) que reemplaza los 4 valores default/tope distintos e inconsistentes que había (notifications 20/50, applications 10/50, candidate-search 20/100, jobs 20/100) por dos parámetros únicos `DEFAULT_PAGE_SIZE` (20) y `MAX_PAGE_SIZE` (100), leídos por los 3 servicios que paginan (`applications-service`, `company-service`, `jobs-service`).

- **Probado:** build limpio en los 4 servicios tocados (`portfolio`, `applications`, `company`, `jobs`) + `libs/common`. `npx jest`: se encontró y corrigió una regresión real (el mock de Prisma en `notifications.service.spec.ts` no tenía `systemParameter.findMany`, causando `TypeError`) — corregida agregando el mock; vuelto a confirmar 40/45 (mismos 5 fallos preexistentes). Verificado en vivo: `GET /admin/parameters` muestra los 2 parámetros de paginación y el de la rúbrica con sus valores/rangos correctos.

### Fase 5 — Seguridad (Nivel 3)
- [x] **Bug real corregido**: `JWT_EXPIRES_IN` estaba declarado en `.env.example`/`.env` desde antes pero `auth.module.ts` hardcodeaba `expiresIn: '1d'` sin leerlo nunca — config muerta. Ahora sí se lee (`jwtExpiresIn = process.env['JWT_EXPIRES_IN'] || '1d'`), sin cambiar el comportamiento actual (el valor en `.env` ya era `'1d'`).
- [x] **Endurecimiento nuevo**: las cuentas ADMIN firman con una sesión de 2 horas (no el `JWT_EXPIRES_IN` general, hoy 1 día) — dado el poder del rol, una sesión abierta y olvidada expira rápido. A propósito NO es un `SystemParameter` editable desde el propio panel (dejar que un admin extienda su propia sesión debilitaría la protección justo donde más importa).
- **Decisión consciente de NO parametrizar en esta fase:** los rate limits (`ThrottlerModule.forRoot(...)`, hoy 10/min login y 300/min general) — técnicamente **no son dinámicamente configurables** sin un refactor más profundo: `ThrottlerModule.forRoot` fija el límite al arrancar el proceso, no por request; hacerlos editables en caliente exigiría un guard custom que lea `SystemParameter` en cada request (con su propio costo de latencia/cache) en vez del `ThrottlerGuard` estándar de Nest. Se decidió **no fingir** una fila de `SystemParameter` para esto que un admin pudiera "editar" sin que tuviera efecto real — eso sería peor que no tener el campo. Queda anotado como trabajo futuro concreto, con el diseño ya pensado (guard custom + cache corto), no como un vacío sin explicar.
- **Probado:** build limpio. `npx jest apps/auth-service`: se encontró y corrigió una regresión real (un test esperaba `jwtService.sign` llamado con un solo argumento; mi primer intento pasaba un segundo argumento `undefined` para roles no-ADMIN, cambiando la firma de la llamada) — corregido separando el branch ADMIN del resto en vez de un argumento condicional. Verificado en vivo decodificando el JWT real: cuenta ADMIN → 2 horas de validez; cuenta CANDIDATE → 24 horas (sin cambio).

### Fase 6 — Integraciones/IA (Nivel 4)
- [x] `DeepSeekService` (compartido, `libs/common`) ya no fija el modelo una sola vez al arrancar el proceso (`process.env['DEEPSEEK_MODEL']`) — ahora `getModel()` lo lee de `SystemParameter` `DEEPSEEK_MODEL` en cada llamada (`chatJson`/`chatText`), con el env var como respaldo si el parámetro no existe. Esto afecta tanto al asistente Joaquín como al análisis de CV, que comparten este servicio.
- **Decisión consciente de NO migrar en esta fase:** remitente/configuración de Brevo — de menor prioridad, ya es env var real (no constante muerta), queda para una fase futura si hace falta cambiarlo sin redeploy.
- **Probado:** build limpio en `common-lib` + los 10 servicios (`build:all` completo, confirma que inyectar `PrismaService` en `DeepSeekService` no rompe ningún módulo — los 10 ya importan `PrismaModule` junto con `CommonModule`). `npx jest`: sin regresiones (ningún spec instancia `DeepSeekService` directamente). Verificado que `GET /admin/parameters` incluye `DEEPSEEK_MODEL` con su valor real actual.

### Fase 7 — Gestión de usuarios (Nivel 5)
- [x] Campo `User.suspended` (migración `20260730010000_add_user_suspended`). `UsersController`/`UsersService` en `admin-service`: listar (filtrable por rol/email, paginado) y `PATCH /admin/users/:id/suspend-state`. **Dos protecciones explícitas**: un admin no puede suspender su propia cuenta (`400`), y no se puede suspender una cuenta ADMIN desde este endpoint en absoluto (`400`) — evita un lockout accidental o un ataque que deje sin acceso a todos los administradores.
- [x] `auth-service`: las 3 funciones de login (`login`/`loginCompany`/`loginAdmin`) rechazan con `403` y un mensaje genérico si `user.suspended` — no antes revela el motivo real más que "está suspendida", el detalle completo (quién, cuándo) queda en `AdminAuditLog`, no en la respuesta al usuario suspendido.
- [x] Nueva página admin "Usuarios y empresas" (`admin-users.component.ts`) — lista con filtro por rol/búsqueda por correo, botón suspender/reactivar con confirmación, oculto para filas con rol ADMIN.
- **Decisión consciente de NO incluir en esta fase:** moderación de ofertas publicadas por empresas y de contenido de chat señalado — alcance mayor (necesitan flujo de "reporte" que hoy no existe en absoluto), quedan para una fase futura.
- **Probado:** build limpio. Verificado en vivo de punta a punta: listar usuarios (paginado, filtrado por email) → suspender un candidato real (`candidato001@demo.com`) → confirmar que su login pasa a `403` con el mensaje correcto → reactivar → confirmar que vuelve a poder loguearse → 2 entradas correctas en `AdminAuditLog` (`SUSPEND_USER`/`REACTIVATE_USER`, antes/después del campo `suspended`). Verificado también (con una cuenta admin fresca, no una con localStorage viejo) que un admin no puede suspender su propia cuenta (`400`).

### Fase 8 — Feature flags (Nivel 6)
- [x] Patrón genérico: cualquier `SystemParameter` de tipo `BOOLEAN` en la categoría `feature-flags` es un flag. Nuevo endpoint `GET /feature-flags` (en `admin-service`, pero **sin** `RolesGuard` — cualquier usuario autenticado, candidato o empresa, necesita poder leerlo) devuelve todos como `{clave: boolean}`. `FeatureFlagsService` (frontend, `providedIn: root`) los carga una vez por sesión de pestaña en un signal.
- [x] Caso real de punta a punta: `FEATURE_ASSISTANT_ENABLED` controla si el asistente Joaquín se muestra — wireado en `app-shell.component.ts`/`.html` y `company-shell.component.ts`/`.html` (`@if (assistantEnabled)` envolviendo el `@defer` existente).
- **Probado:** build limpio. **Se detectó y corrigió un problema real del entorno de pruebas** durante esta verificación: el servidor de desarrollo (`ng serve`) había quedado con una compilación incremental corrupta desde ediciones anteriores (mostraba errores de TypeScript ya resueltos hace varias fases, con el código fuente real ya corregido) — un reinicio limpio del servidor lo confirmó. Esto significa que las verificaciones "en vivo contra el navegador real" de las Fases 3 y 7 hasta ese punto se habían apoyado en llamadas directas a la API (que sí prueban el backend end-to-end) pero no habían confirmado la UI real renderizando correctamente — se re-verificaron ambas páginas (`/admin/catalogs`, `/admin/users`) contra el servidor ya reiniciado y limpio, con resultado correcto. Verificado en vivo (ya con el servidor sano): con el flag en `true`, Joaquín aparece en `/app/inicio`; poniéndolo en `false` desde el panel, desaparece sin recargar código (solo con la próxima navegación); reactivado, vuelve a aparecer.
